## نبذة عن التكليف

يقدّم هذا العمل شرحًا بصريًا ومنظّمًا للفرق بين **المكتبة (Library)** و**إطار العمل (Framework)**؛ بدءًا من التعريف وآلية التحكّم في التنفيذ، وصولًا إلى أمثلة من لغات ومنظومات مختلفة، وهيكل المشروع، والاعتماديات، ومعايير اختيار الأداة المناسبة.

يضم المستودع تصميمين متكاملين: نسخة إبداعية موجزة لشرح الفكرة الأساسية، ونسخة مرجعية موسّعة للمراجعة والتعلّم. الشرح بالعربية، مع إبقاء أسماء الأدوات والمصطلحات البرمجية باللغة الإنجليزية لتسهيل البحث والرجوع إلى التوثيق الرسمي.

> **الخلاصة:** تستدعي المكتبة من كودك، بينما يوفّر إطار العمل دورة تشغيل يستدعي خلالها الأجزاء التي تكتبها. هذه قاعدة تعليمية مفيدة، وليست حدًّا فاصلًا مطلقًا بين كل الأدوات.

## أهداف التعلّم

- التمييز بين دور Library ودور Framework في بناء التطبيقات.
- فهم مفهوم **Inversion of Control** وتأثيره في تدفّق التنفيذ.
- مقارنة المرونة، وتنظيم المشروع، والتعلّم، وصعوبة الاستبدال.
- التعرف على أمثلة شائعة ضمن لغات ومنظومات برمجية مختلفة.
- فهم العلاقة بين الأطر والمكتبات والاعتماديات.
- ربط اختيار الأدوات بقابلية الصيانة، والأمان، ومتطلبات المشروع.

## المحتوى العلمي

### ما هي Library؟

مجموعة من الوظائف أو الأصناف أو المكوّنات القابلة لإعادة الاستخدام. يستدعيها كودك لإضافة قدرة، مثل إرسال طلبات HTTP، أو معالجة البيانات، أو بناء واجهات المستخدم.

**مثال:** استخدام Requests في Python لإرسال طلب HTTP.

### ما هو Framework؟

بنية وأدوات واتفاقيات تساعد على بناء تطبيق ضمن نمط ودورة عمل محدّدين. تكتب الأجزاء المطلوبة، ويستدعيها الإطار في سياقات مثل استقبال الطلبات أو معالجة الأحداث.

**مثال:** استخدام Flask لتعريف مسارات تطبيق ويب والدوال التي تُنفَّذ عند وصول الطلبات.

### الفرق الجوهري: Inversion of Control

الفكرة هي انتقال جزء من مسؤولية إدارة التنفيذ إلى الإطار، وليست فقدان المطوّر القدرة على اتخاذ القرارات. وقد تستدعي بعض المكتبات أيضًا دوال يكتبها المطوّر عبر Callbacks؛ لذلك لا يُحسم التصنيف من استدعاء واحد فقط، بل من دور الأداة في التطبيق ككل.

### مقارنة عملية

| وجه المقارنة | Library | Framework |
| --- | --- | --- |
| التحكّم بالتنفيذ | تديره أنت غالبًا | يدير الإطار جزءًا كبيرًا منه |
| الدور | إضافة وظيفة أو قدرة | توفير أساس ومنظومة لبناء التطبيق |
| تنظيم المشروع | تختار طريقة التنظيم والدمج | يوفّر اتفاقيات أو نمطًا للبناء |
| المرونة | حرية أكبر في طريقة الدمج غالبًا | مرونة ضمن قواعد الإطار |
| الاستبدال | أسهل غالبًا عند عزل الاعتماد عليها | أصعب غالبًا عند ارتباط بنية التطبيق به |
| الحجم والنطاق | قد تكون صغيرة أو واسعة | يشمل عدة جوانب من التطبيق عادةً |
| التعلّم | تتعلّم API التي تحتاجها | تتعلّم الاتفاقيات ودورة العمل والأدوات |

هذه فروق إرشادية وليست ضمانات. لا يعني استخدام Library تلقائيًا أداءً أفضل أو حجمًا أصغر، ولا يعني استخدام Framework أن تنظيم المجلدات ثابت دائمًا.

### أمثلة حسب اللغة والمنظومة

| اللغة / المنظومة | أمثلة Library | أمثلة Framework |
| --- | --- | --- |
| JavaScript / TypeScript | React · Axios · Lodash | Angular · NestJS |
| Python | NumPy · Requests · Pandas | Django · Flask · FastAPI |
| PHP | Guzzle · Carbon | Laravel · Symfony |
| Java | Jackson · Guava | Spring Boot · Quarkus |
| C# / .NET | Dapper · Newtonsoft.Json | ASP.NET Core |
| Ruby | Faraday · Nokogiri | Ruby on Rails · Hanami |
| Dart | http · intl | Flutter |
| C++ | fmt · Eigen | Qt |

**ملاحظات مهمة:**

- القائمة تمثيلية، ولا تشمل جميع اللغات أو جميع الأدوات.
- React مكتبة لبناء واجهات المستخدم، وليست بمفردها إطارًا متكاملًا للتطبيق.
- Qt منظومة تتضمن مكتبات وأطرًا متعددة؛ بعض التصنيفات تحتاج إلى هذا التفصيل.
- شمول المكتبة لعدد كبير من الوظائف لا يجعلها تلقائيًا Framework.

### مثال برمجي: الاستدعاء المباشر مقابل الاستدعاء بواسطة الإطار

**Library — Python Requests:** يبدأ كودك الطلب باستدعاء الوظيفة.

</div>

```python
import requests

response = requests.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)
```

<div dir="rtl">

**Framework — Python Flask:** يربط الإطار المسار بدالة يستدعيها عند وصول طلب مطابق.

</div>

```python
from flask import Flask

app = Flask(__name__)

@app.get("/hello")
def hello():
    return {"message": "Hello"}

if __name__ == "__main__":
    app.run()
```

<div dir="rtl">

الأمثلة للتعلّم المحلي، وليست إعدادًا جاهزًا للإنتاج. يتطلب تشغيلها تثبيت الحزم المطلوبة. يجب استخدام إعداد نشر مناسب لتطبيق Flask عند تشغيله في بيئة إنتاجية.

### هيكل المشروع والاعتماديات

عند استخدام مكتبة، تختار غالبًا تنظيم الملفات ومواضع دمجها. أمّا إطار العمل، فقد يقدّم اتفاقيات أو بنية مقترحة تساعد الفريق على توحيد العمل. هيكل MVC الظاهر في التصميم مثال توضيحي، وليس تنظيمًا إلزاميًا لجميع الأطر.

يمكن أن يحتوي Framework على عدة Libraries، ويمكن للتطبيق أن يجمع أطرًا مختلفة لطبقات مختلفة، مثل الواجهة والخادم. ومع ذلك، يجب مراجعة توافق الإصدارات، والتراخيص، والاعتماديات المباشرة وغير المباشرة؛ لأن المكتبات قد تتعارض فيما بينها أيضًا.

### كيف تختار؟

**اختر Library عندما:** تحتاج قدرة محددة، أو تعمل على بنية قائمة، أو تريد حرية أكبر في اختيار الأدوات وطريقة دمجها.

**اختر Framework عندما:** تحتاج أساسًا متكاملًا، واتفاقيات مشتركة للفريق، وأدوات تقلّل العمل المتكرر.

**قبل القرار، قيّم:** متطلبات المشروع، وخبرة الفريق، وجودة التوثيق، واستمرارية الدعم، وقابلية الاختبار، والصيانة والأمان، والأداء الفعلي.

## الصلة بالأمن السيبراني

فهم المكتبات وأطر العمل يساعد على فهم **سلسلة توريد البرمجيات (Software Supply Chain)** وحدود الثقة داخل التطبيق. لا يُعد أيٌّ منهما آمنًا أو غير آمن لمجرد تصنيفه؛ بل تعتمد المخاطر على الأداة وإصدارها وإعدادها وطريقة استخدامها.

من الممارسات المهمة:

- تنزيل الحزم من مصادر موثوقة والتحقّق من أسمائها لتجنّب الحزم المقلّدة.
- متابعة التنبيهات الأمنية وتحديث الاعتماديات وفق اختبار وتقييم مناسبين.
- استخدام ملفات القفل (Lockfiles) عندما تدعمها المنظومة لتحسين قابلية إعادة البناء.
- مراجعة الاعتماديات غير المباشرة، لا الحزم المضافة مباشرة فقط.
- عدم رفع المفاتيح السرية أو كلمات المرور أو ملفات الإعداد الحساسة إلى المستودع.
- عدم افتراض أن وسائل الحماية التي يوفّرها الإطار تعوّض مراجعة الكود والإعدادات.
